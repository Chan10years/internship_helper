## 1. 一句话结论

这是一个已经能演示并实际使用的本地单用户 MVP，但还不是可以直接部署给真实用户的在线产品。

不建议推倒重写。当前采集、评分、存储、API 和界面的基本分层是成立的；真正需要的是先纠正文档与实现的阶段漂移，再用“模块化单体”方式逐步补齐数据库边界、账号与权限、后台任务、安全、监控、备份和真实端到端测试。

当前最大问题不是“代码太多”，而是以下四点：

1. 产品阶段与仓库事实不一致：正式文档禁止当前阶段引入数据库，但仓库已存在 PostgreSQL 依赖、用户/会话/收藏等表和导入命令。
2. 数据质量不足：16 条岗位中，城市、薪资、周期、学历、到岗天数均只有 62.5% 完整度，标签完整度为 0%。
3. 测试结论容易被高估：47 项测试全部通过，但浏览器端主要依靠源码字符串检查，核心采集编排和真实数据库都没有被完整集成验证。
4. 在线产品基础尚未实现：没有真正的账号系统、权限隔离、数据库读写主链路、任务队列、部署、安全防护、监控、备份和隐私删除流程。

## 2. 产品状态判定

### 2.1 当前真正拥有的产品

当前产品是“本地岗位信息查看与初筛工具”，核心用户流程为：

```text
平台配置采集条件
  -> Playwright 可见浏览器采集
  -> 站点适配器解析为统一岗位结构
  -> 本地规则评分和简历建议
  -> JSON 合并去重 + CSV 导出
  -> Express 提供 /api/jobs
  -> 原生 Web 页面搜索、筛选、排序和查看详情
```

这条链路能够运行。2026-07-21 的模拟验证中：

- TypeScript 类型检查通过。
- 47/47 项自动测试通过。
- 进程内调用 `/api/jobs` 返回 HTTP 200、状态 `ready` 和 16 条岗位。
- 真实 Chromium 页面加载出 16 条岗位，筛选抽屉、搜索输入和详情弹层可交互。
- 生产依赖的 npm 官方漏洞审计结果为 0 个已知漏洞。

### 2.2 当前不应被描述成的产品

它不是以下产品：

- 不是已上线网站。
- 不是多用户系统。
- 不是拥有完善数据库主链路的系统。
- 不是已经完成用户身份、收藏、投递状态和简历隐私保护的产品。
- 不是具备无人值守、可恢复、可监控后台采集能力的平台。
- 不是已经验证可承载 1000 名注册用户的产品。

## 3. 架构总览与评价

### 3.1 做得好的部分

现有本地架构已经具备合理的职责分离：

- `src/crawler/` 负责站点采集和标准化，不直接保存文件。
- `src/crawl/` 负责编排采集、评分、合并和导出。
- `src/scoring/` 是无网络、可解释的纯规则逻辑。
- `src/storage/` 负责 JSON/CSV，而不是混入爬虫。
- `src/server/` 只读取已有岗位，不允许网页触发爬虫。
- `src/auto/` 对相同采集流程做定时包装，并能避免单进程内重叠运行。
- 数据写入采用临时文件再重命名，降低文件写坏风险。
- 前端使用 `textContent` 等安全 DOM API，来源链接仅允许 HTTP/HTTPS。

这些边界值得保留，是“不需要全面重写”的主要原因。

### 3.2 当前架构的主要断点

#### P0：产品决策与代码事实冲突

正式文档将数据库、账号和多用户能力放在未来阶段，并明确禁止当前本地阶段引入数据库；但当前仓库已经：

- 在生产依赖中加入 `pg` 和 `@types/pg`。
- 增加 PostgreSQL 迁移、导入和验证命令。
- 创建 `users`、`sessions`、`favorites`、`application_statuses` 等未来阶段表。
- 增加数据库相关测试。

同时，文档优先级声明中的 `docs/13_DECISIONS.md` 并不存在，因此无法确认这次提前实现是否经过产品批准。

影响：团队会同时维护“JSON 是当前唯一存储”和“数据库已经开始建设”两套叙事，后续人员无法判断哪条路线有效，也容易继续在未定产品范围上投入。

建议：在继续开发前先做一次产品决策，二选一：

1. 仍处本地完善阶段：将数据库代码明确标为隔离的实验，不接入主链路，文档说明其非当前交付范围。
2. 正式进入数据库迁移阶段：更新产品阶段、技术栈、验收标准和决策记录，再按新的架构边界继续实现。

不建议在未决策时继续扩充账号、会话或收藏代码。

#### P0：在线架构没有形成可工作的主链路

数据库代码目前只完成了建表、JSON 映射和导入命令。Web API 仍然直接读取 `data/internships.json`，采集完成后也只写 JSON/CSV。也就是说，数据库并不是系统运行时的数据来源。

当前状态更接近“数据库概念验证”，而不是“数据库迁移完成”。

#### P1：缺少稳定的应用与存储接口

`runCrawl` 直接依赖文件加载、文件保存和 CSV 导出；`server` 也直接读取 JSON 文件。未来切到 PostgreSQL 时，如果继续直接替换调用，采集、API 和迁移代码会互相牵连。

建议增加小而明确的边界概念，而不是引入大型框架：

```text
应用用例
  JobCatalog（读取岗位、合并岗位、标记状态）
      ├─ LocalJsonJobRepository（当前本地实现）
      └─ PostgresJobRepository（未来在线实现）

采集适配器 -> CollectJobs 用例 -> JobCatalog
Web API     -> BrowseJobs 用例  -> JobCatalog
CSV 导出    -> ExportJobs 用例  -> JobCatalog
```

这样可以保留现有代码，同时让 JSON 与 PostgreSQL 可切换、可对照验证。

#### P1：共享评分与个性化评分概念混在一起

当前规则中包含偏好的技能、地区和个人背景倾向，但结果直接写回共享岗位的 `matchScore`、`matchReasons` 和 `resumeAdvice`。对当前单用户本地工具是可接受的，对多用户产品则不成立。

在线阶段应拆成：

- 岗位共享事实：岗位名称、城市、要求、标签、有效状态等。
- 通用质量或相关度：可选，但必须说明规则版本和目标主题。
- 用户匹配结果：按 `user_id` 或 `preference_profile_id` 单独保存，并记录规则版本和计算时间。

否则不同用户会看到同一份“看似个性化、实则固定”的匹配分。

#### P1：稳定标识尚不足以支撑用户收藏和历史关系

本地合并以精确链接优先，否则使用 `title + company + city`。这对 16 条数据够用，但存在以下问题：

- 链接查询参数、尾斜杠或来源 URL 变化会生成新的身份。
- 标题、公司名称或城市轻微改名可能生成重复岗位。
- 合并时岗位 `id` 可能被新记录覆盖；在线收藏、投递状态等外键不能依赖这种可变化标识。

在线数据库应使用不可变内部主键，并把来源岗位 ID、规范化 URL、来源与业务指纹作为独立去重字段。

#### P1：采集编排的失败隔离不足

当前任一启用来源抛错会终止整个 `runCrawl`，不会形成明确的逐来源运行记录。定时器只防止同一进程内重叠，无法防止两个进程或未来多个实例同时采集。

本地阶段建议至少记录每个来源的开始、成功、失败和数量；在线阶段由后台任务表或队列提供任务锁、重试上限、暂停、心跳和运行历史。

#### P2：配置合同与实际行为不完全一致

- `CrawlConfig.cities` 已定义，但当前两个采集适配器都没有真正按城市使用它。
- BOSS 适配器没有使用 `maxPages`，且选择器仍明确处于未验证状态。
- 这些字段容易让使用者误以为功能已经生效。

建议把“已经生效的配置”和“为未来保留的配置”明确区分，未实现项不应出现在可操作产品承诺中。

#### P2：运行时数据校验不足

服务端只验证 JSON 顶层是不是数组，没有验证数组中的岗位字段。TypeScript 只在编译期有效，不能保护从文件或数据库读入的真实数据。

例如 `tags` 若变成字符串、`id` 重复或日期无效，前端可能在运行时出错或产生错误选择状态。在线 API 必须加入统一的输入/输出校验；本地阶段也应至少对导入和读取数据做结构验证并报告具体错误。

#### P2：服务端错误与运维能力只适合本地

当前服务没有统一的 404/错误响应策略、请求日志、请求 ID、健康检查、关闭流程、限流、安全头或生产配置。日志是两个持续追加的文本文件，没有轮转和结构化上下文。

这不是本地 MVP 的缺陷，但属于上线阻断项。

## 4. 代码规模、冗余与可维护性

### 4.1 是否存在“大量冗余”

结论：没有发现大量复制粘贴式业务代码，当前问题主要是文件过大和提前实现，而不是全面冗余。

本次统计的源码、测试、HTML、CSS、JavaScript 合计约 4488 行，其中：

- `style.css`：1355 行。
- `app.js`：576 行。
- `shixisengCrawler.ts`：400 行。
- 数据库实现：约 330 行，另有 67 行数据库测试。

需要关注的点：

1. `style.css` 和 `app.js` 已接近需要拆分的临界点。它们仍可维护，但后续再加入登录、收藏、投递状态会快速恶化。
2. `shixisengCrawler.ts` 同时包含 URL、列表抽取、详情抽取、字段解析和浏览器编排，建议在继续扩展来源前按“浏览器访问 / 原始数据 / 纯解析”拆开。
3. 数据库代码是当前最明显的“提前投入”，但不应直接删除；应先确认产品阶段，再决定保留为实验、补齐为正式迁移，或重新调整表设计。
4. 评分信号中有小规模重复，例如“实习证明”重复出现；这类冗余不严重，但说明规则需要集中配置、版本化和解释。

### 4.2 目前不应急着做的重构

- 不需要改成微服务。
- 不需要 Kubernetes。
- 不需要为了“现代化”立即换 React、Vue 或 Next.js。
- 不需要引入复杂领域驱动框架。
- 不需要同时支持多种数据库。
- 不需要先做缓存；目标并发量下，正确索引的 PostgreSQL 足够。

## 7. 推荐的目标架构

推荐“模块化单体 + PostgreSQL + 独立后台运行入口”，不推荐微服务。

```text
浏览器
  -> Web 静态资源 / 页面
  -> HTTP API
       -> 认证与权限
       -> 应用用例
            ├─ 岗位浏览与搜索
            ├─ 用户偏好与收藏
            ├─ 用户匹配与简历建议
            └─ 导出
       -> PostgreSQL

平台调度器 / 管理员
  -> 后台任务入口
       -> 采集适配器
       -> 解析与质量检查
       -> 共享岗位库
       -> 运行记录、错误与告警
```

关键原则：

- 一个代码仓库、一个产品，不拆微服务。
- Web API 与后台采集可以是同一套代码的两个启动入口；需要时再部署为两个进程。
- 共享岗位与用户私有数据分表、分权限。
- 普通用户永远不能直接启动 Playwright。
- 所有用户共享一份岗位目录，用户只保存偏好、收藏、投递状态和自己的匹配结果。
- 数据库使用不可变内部主键；来源身份和去重规则作为可演进字段。
- 先以数据库任务表和受控调度完成可靠性；只有出现真实吞吐或并发问题时再决定是否引入专门队列/Redis。
- 前端当前可继续使用原生技术；当账号、收藏、投递状态等交互显著增加时，再评估组件化框架是否降低长期成本。

## 8. 产品范围与人员分工

### 8.1 必须由产品经理决定

- 下一阶段究竟是“本地完善”还是“正式数据库迁移”。
- 第一批在线用户是谁：仅自己、邀请制学生，还是公开注册。
- 第一版核心价值是岗位聚合、匹配推荐、申请管理，还是三者组合。
- 匹配分针对哪类用户，是否需要用户偏好，如何解释分数。
- 是否存储简历全文或文件；保存多久，用户如何导出和删除。
- 是否继续投入 BOSS 适配器验证。
- 标签是产品核心筛选能力，还是暂时取消。
- 上线地区、使用条款、隐私说明和数据来源展示要求。

### 8.2 建议的小团队分工

最小可行团队不需要很多人，但职责必须有人明确承担。

| 角色 | 主要责任 | 可否兼职 |
| --- | --- | --- |
| 产品经理 | 用户、范围、优先级、验收、来源政策、匹配解释 | 不建议缺席 |
| 全栈/技术负责人 | 架构边界、API、代码质量、安全基线、发布门槛 | 可兼后端 |
| 数据采集负责人 | 来源适配、解析质量、采集策略、运行诊断 | 可由后端兼任 |
| 前端负责人 | 搜索详情、账号与个人工作流、响应式与无障碍 | 可由全栈兼任 |
| QA | 验收案例、真实浏览器回归、异常和越权测试 | 早期可兼职 |
| 运维/安全 | 部署、HTTPS、监控、备份恢复、密钥和事故响应 | 早期可由技术负责人兼职 |

如果只有一名开发者：按阶段串行承担全栈、采集、测试和运维角色，但每个阶段都应有独立验收清单，避免“写完代码的人顺手宣布上线”。

## 9. 上线路线图与工作量

以下估算以 1 名有经验的全栈开发者为主、产品经理持续参与、已有代码继续复用为前提；如果开发者同时学习 Web 基础，日历时间应按约 1.5–2 倍考虑。

### 阶段 0：产品与仓库纠偏（2–4 天）

- 记录是否正式进入数据库阶段。
- 修正文档中的 10/16 条数据、数据库状态和验收口径。
- 明确第一版在线用户和功能范围。
- 给现有数据库代码标明“实验”或“正式迁移”。
- 建立发布阻断项列表。

出口：任何新开发者都能明确说出“当前阶段、当前主存储、当前交付目标”。

### 阶段 1：本地产品稳定化（1–2 周）

- 提升结构字段完整度，补数据质量统计。
- 处理标签能力的保留或移除。
- 拆分实习僧解析与浏览器访问，增加固定页面样本测试。
- 为采集主流程增加失败隔离和运行摘要。
- 加入真实浏览器关键流程测试。
- 补运行时数据校验。

出口：本地产品可重复运行，页面变化或坏数据能明确报错，不会静默产生“看似正常”的结果。

### 阶段 2：数据库岗位目录（2–3 周）

- 审核并重做可版本化迁移策略。
- 先只实现共享岗位、来源、采集任务/运行记录等当前必要实体。
- 建立 `JobRepository`/`JobCatalog` 边界。
- 完成 JSON -> PostgreSQL 导入、校验、回滚方案。
- API 从数据库读取；CSV 从同一岗位目录导出。
- 建立真实 PostgreSQL 集成测试和备份恢复演练。

出口：数据库成为受测试的岗位主数据源，JSON 仍有清晰的回退或归档策略。

### 阶段 3：邀请制账号与个人工作流（2–4 周）

- 注册策略、登录、退出、密码重置或邀请流程。
- 安全会话、CSRF/等效保护、限流和统一输入校验。
- 用户偏好、收藏、投递状态。
- 用户数据授权测试，确保任何用户不能访问他人记录。
- 将用户匹配结果从共享岗位中拆出。

出口：少量邀请用户可以安全使用，且私有数据隔离有自动测试。

### 阶段 4：后台任务与运营能力（2–3 周）

- 平台级定时采集，普通用户无采集权限。
- 任务去重、锁、重试上限、暂停和运行历史。
- 运营者可看到来源失败、解析质量和数据更新时间。
- 岗位最后发现时间和失效状态。

出口：无需人工盯住进程，也不会因失败无限重试或多实例重复运行。

### 阶段 5：部署与小范围 Beta（2–4 周）

- 生产环境、域名、HTTPS、安全 Cookie、密钥管理。
- 请求日志、错误监控、健康检查、告警。
- 数据库自动备份、恢复演练和用户删除流程。
- 20–50 并发的基础压测。
- 隐私说明、来源说明、服务条款和反馈入口。
- 小范围 Beta 与修复周期。

出口：达到“可以邀请真实用户承担有限风险试用”，而不是仅仅“服务器能打开”。

### 总体时间判断

- 达到稳定本地产品：约 1–2 周。
- 达到邀请制在线单用户/管理员版：累计约 4–7 周。
- 达到小范围多用户 Beta：累计约 8–12 周。
- 达到较稳妥的 1000 注册用户公开版本：累计约 12–18 周，并取决于 Beta 暴露的问题。
- 单人边学边做：更现实的日历时间为 4–8 个月。

目标的 20–50 常态并发并不要求复杂分布式架构。决定进度的不是服务器扩容，而是产品范围、数据质量、认证授权、隐私、后台任务和运维闭环。

## 10. 优先级清单

### 现在必须做

1. 产品经理确认阶段：本地完善或数据库迁移。
2. 建立有效决策记录，解释现有 PostgreSQL 代码和依赖来源。

2. 运行时数据结构校验。

4. 把纯解析逻辑从浏览器控制中拆出并增加样本测试。
5. 增加真实浏览器端到端测试。
6. 用正式迁移和真实 PostgreSQL 集成测试替代 SQL 字符串检查。

1. 是否启用 BOSS直聘。
2. 是否换前端框架。
3. Redis、缓存和独立队列产品。
4. 微服务、Kubernetes 和分布式系统。
5. LLM 简历建议。

## 11. 最终建议

建议批准“纠偏 + 模块化演进”，不批准全面重写，也不建议继续无边界地提前建设多用户功能。

推荐的产品决策顺序是：

1. 先把当前阶段说清楚。
2. 再把本地数据质量和异常可见性做好。
3. 然后只迁移共享岗位目录到 PostgreSQL。
4. 之后增加邀请制账号、收藏和投递状态。
5. 最后补齐后台任务、部署、安全、监控、备份、隐私和 Beta 验证。

现有项目已经证明“这个方向可以做出来”，但还没有证明“可以安全、稳定地让真实用户长期使用”。下一阶段的价值不在于增加更多页面或更多表，而在于把产品边界、数据可信度和运行可靠性变成可验证的系统能力。
